# TODO: Grounding the LLM Response

## The Concern

The conversational response is generated by an LLM. We can constrain *which supplements* it
names, but we currently do **not** constrain the *factual content* of what it says about them.
The LLM is free to invent or overstate mechanisms, studies, and effects — "freelancing" facts
beyond what we passed it. This has been observed in practice.

The governing principle we want to enforce:

> **The LLM must never state a factual claim beyond what we explicitly pass it.** Everything in
> the response must be grounded in our facts.

This document traces where response content comes from, what we tell the LLM to do with it,
where the gaps are, and a proposed approach for closing them.

---

## Background: Where the Sources Come From

The response prompt is assembled in `intake-agent/src/context.rs` (`build_context_v2`). The
factual content it contains is fetched by `graph-service/src/intake/executor.rs`
(`ActionResults`), which calls the supplementology API. The pieces:

| Section in prompt | Built by | Source (supplementology) |
|---|---|---|
| Ranked candidates | recommendation traversal | `is_effective_for`→symptom edges + graph patterns |
| Drug interactions (+ description text) | `executor::fetch_interactions` | `interacts_with` edges (iDISK) |
| Adverse reactions | `executor` adverse match | `has_adverse_reaction` edges |
| **MECHANISM OF ACTION** (free text) | `executor::fetch_mechanisms` → `api.mechanism_of_action()` | `narrative_text` table, `text_type='mechanism_of_action'` (**iDISK-sourced**) |

The mechanism-of-action narrative is the key one: it is **free prose**, ~500 chars, fetched per
candidate from `/rpc/ingredient_narratives` and dropped into the prompt under
"MECHANISM OF ACTION (sourced — use to explain WHY, not to fabricate)". It is the richest factual
material the LLM is handed, and the material it is most invited to elaborate on.

## What We Tell the LLM (Rendering Instructions)

The full system prompt is built in `context.rs`. Top to bottom:

1. **ROLE** — "a supplement intake specialist… identify supplements that may help."
2. **COMMUNICATION STYLE** — short, warm, one question per turn, plain language, no markdown.
3. **LEGAL CONSTRAINTS** —
   - Never diagnose / never "you have [condition/disease/disorder]."
   - Never "cure." *"Supplements address symptoms, not diseases."*
   - Never "take X" / "you should try X" — report findings instead.
   - Emergency → 911. Never recommend dosages.
4. **DATA SECTIONS** — chief complaints, candidates, interactions, adverse reactions, mechanism
   narratives.
5. **YOUR TASK THIS TURN** (recommendation phase) —
   - `PERMITTED SUPPLEMENTS — YOU MAY ONLY MENTION THESE: …` (hard whitelist)
   - "Present what the research suggests… you are REPORTING findings, not prescribing."
   - Evidence-scope honesty (`evidence=specific` vs `evidence=general`).
   - "Use the MECHANISM OF ACTION text above for sourced explanations."

Enforcement that exists today (`intake-agent/src/safety.rs`), run on the LLM output:
- **Blacklist regex** — catches diagnostic *phrasing* ("you have…", "cure", "diagnose",
  "take N mg") → Block or Rewrite.
- **Ingredient whitelist** — n-gram scan blocks any supplement name not in the permitted set.

## The Problems

**1. Grounding is encouraged, not required.**
"Use the MECHANISM OF ACTION text above" tells the LLM what it *may* draw on; it never says the
response must contain *only* facts present in the data. There is no instruction equivalent to
"do not introduce any mechanism, study, or claim from your own knowledge." So elaboration is
permitted by omission.

**2. Enforcement covers names, not claims.**
safety.rs structurally guarantees the LLM can't name an off-list *supplement* (whitelist +
n-gram block). There is no analogous check that a *factual sentence* traces back to a fact we
provided. The system knows every supplement name to police; it knows nothing about which claims
are grounded.

**3. The blacklist is phrasing-based, not entity/claim-based.**
It catches the *shape* of a diagnosis ("you have a deficiency") but not a fabricated or
overstated fact stated in fluent, legal-sounding prose ("magnesium corrects the underlying
cellular energy deficit") — no trigger phrase, no off-list supplement, passes clean.

**4. The mechanism narrative is an unattributed blob.**
It is passed as one prose string per ingredient, not as discrete attributable facts. Even if we
wanted to verify the output against it, there is no claim-level structure to verify *against* —
we can't currently ask "does this sentence map to a fact we passed?" because the facts aren't
individuated.

**5. (Related) The disease-talk constraint is now stricter than our intended policy.**
LEGAL CONSTRAINTS says "supplements address symptoms, not diseases," a blanket ban on disease
talk. Our intended policy is narrower: we *may* surface disease-related research as **cited
educational material** (e.g. "a 2019 RCT found X reduced blood pressure in participants with
hypertension"), but must never **diagnose** the user or **prescribe** a treatment for a disease.
Closing the grounding gap is a prerequisite for safely relaxing this: cited disease research is
only acceptable if the citation is real and the claim cannot be freelanced.

---

## Proposed Solution: Two-Call Generate + Verify

Split response construction into two LLM calls:

**Call 1 — Generate (longer).**
The existing response generation, plus an explicit **grounding instruction**: state only facts
present in the provided data; do not introduce mechanisms, studies, effects, or claims from
outside knowledge. (Prompt-level half — necessary, not sufficient.)

**Call 2 — Verify (shorter, cheaper).**
A separate call that receives (a) the grounding facts we passed and (b) the generated response,
and checks that every factual claim in the response is supported by the grounding. It returns a
structured verdict — pass, or a list of unsupported/overstated claims. On failure: regenerate
with the specific violations fed back, or fall back to a safe canned response.

This mirrors the structure that already works for supplement names (constrain in the prompt,
enforce after generation), extended from *names* to *claims*. The verifier is deterministic in
spirit even though it's an LLM: its only job is "is this claim in the source — yes/no," which is
a narrower, more reliable task than open generation.

### Prerequisites / open design questions

- **Claim-level grounding (Problem 4).** The verifier is only as good as the attributability of
  what we pass. Likely need to pass facts as individuated, sourced units (with IDs/citations)
  rather than a prose blob, so the verifier — and eventually a citation panel — can map a
  response sentence back to a specific source.
- **Cost / latency.** Two calls per turn. The verify call should be small and fast (cheaper
  model, short context). Possibly only run verification on the recommendation/explanation turns,
  not every gather-info turn.
- **Failure policy.** Regenerate-with-feedback vs. block-to-canned, and how many retries before
  falling back.
- **Interaction with safety.rs.** The verifier complements, not replaces, the existing
  phrasing/name checks; decide ordering (cheap regex first, then verify).
